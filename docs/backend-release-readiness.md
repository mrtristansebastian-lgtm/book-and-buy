# Butler and website builder release handoff

Implementation prepared on 8 October 2026. Deployment was authorized on 8 October; the production release record is in `docs/releases/2026-10-08.md`. This document distinguishes local implementation from external service verification.

Local verification: the integrated suite passed **614 checks with zero failures or skips**. The final AI/builder safeguards then passed **39 focused checks with zero failures or skips**. TypeScript, health/smoke checks, and the final production build passed. The backend runner passed all **67 integration checks** with provider network calls blocked. Desktop and 390px browser checks confirmed working builder controls, readiness, an expanding mobile composer, gated AI connection cards, and no page overflow or broken images. Browser checks used the local demo; they do not verify real Google, Storage, payment, or ChatGPT account connections.

## Implemented behavior

- Owner workspace commands retain section revisions, retry receipts, and collection migration epochs. Cloud hydration is scoped to the authenticated owner. Unsaved edits survive refresh; concurrent changes require an explicit comparison before reapplying or discarding.
- Butler and the website runtime use the same authoritative booking, order, market, inventory, and payment handlers. Stock reservations expire, verified payment commits once, and late payments either reacquire available stock or enter an owner-visible exception.
- Butler reads are bounded; its write tools prepare inline reviews. Applying a proposal rechecks ownership, current revisions, and permissions. Routine automations have specified records and allowed fields, frequency, daily limits, expiry, pause controls, deduplication, and execution history. Expired permissions and exhausted daily limits leave the due queue. Daily counters use UTC.
- Website source, files, and assets save into private immutable Storage versions through owner callables. Save, publish, preview, and rollback retry keys survive interrupted responses. Cloud versions can be restored; incompatible drafts remain editable and cannot publish.
- The public renderer uses a dedicated origin and a sandboxed frame. Its validated commerce bridge accepts IDs/selections; server handlers calculate business decisions. Checkout status requires an independent random capability token. Public previews expire after 24 hours and cannot mutate commerce.
- The AI gateway stores protected provider credentials, model-specific reasoning settings, conversations, durable runs, allowance reservations, explicit cancellation, and recovery. Conversations are partitioned by owner, provider, connection revision, and mode. Disconnect or a billing/account change requires a new conversation. Navigation does not silently cancel a server run or switch billing.
- Google app sign-in recovers redirect intent and exposes failures. Authenticated pages wait for the correct owner's cloud workspace before routing to onboarding or autosaving.

Capability coverage is recorded in `functions/workspaceDomain.js`. Refunds, payouts, subscription upgrades, email/SMS automations, carrier labels, tax calculation, currency conversion, authenticated staff delegation, and AI file/vision attachments remain unavailable. They do not return simulated success. Website source/file/asset import works separately; imported project files are not advertised as AI attachment understanding.

## External setup before a release

1. Configure the production Firebase web app, Storage bucket, and matching `VITE_APP_ID` / server `APP_ID`. Enable Google and email/password authentication. Use the owner's Firebase Hosting domain as `authDomain`, authorize that domain, and register its exact `https://<owner-domain>/__/auth/handler` redirect. Verify popup and redirect flows with a real account in a separate signed-out browser. [Firebase redirect guidance](https://firebase.google.com/docs/auth/web/redirect-best-practices).
2. Create a **second** Firebase Hosting site. Bind the existing `storefront` target in `.firebaserc` to that site. `firebase.json` already contains its renderer and `/api/website` gateway rewrite. Set `APP_PUBLIC_BASE_URL` and `WEBSITE_PUBLIC_BASE_URL` to distinct HTTPS origins. Never route generated websites onto the owner's authenticated origin.
3. Set the non-secret function configuration from `functions/.env.example`. Put `AI_SETTINGS_ENCRYPTION_KEY` and funded `OPENAI_API_KEY` in Google Secret Manager. Preserve the encryption key across redeployments; replacing it without a credential migration prevents decryption of existing connections. Configure actual project-accessible model IDs and reasoning capabilities using the [official model catalog](https://developers.openai.com/api/docs/models). Included AI needs explicit `AI_INCLUDED_PROVIDERS=openai` and a positive `AI_INCLUDED_DAILY_TOKENS` budget. An owner's own OpenAI API connection uses its separate secure settings flow.
4. Keep `AI_CHATGPT_OAUTH_ENABLED=false` and `AI_CHATGPT_INFERENCE_APPROVED=false` while OpenAI partner approval is pending. Commercial ChatGPT sign-in and plan-backed inference require approved registration. After approval, configure the provided `oaiapp_...` client ID, authentication method, exact first-party `/api/ai/chatgpt` callback, return URL, and separate inference permission. Identity approval alone does not fund model calls. [Official commercial integration documentation](https://developers.openai.com/siwc/website), [quickstart](https://developers.openai.com/siwc/quickstart). Claude is outside this release.
5. Deploy the functions, Firestore rules/indexes, Storage rules, and both Hosting sites as one staged release once deployment is authorized. Confirm scheduled functions `expireStockHolds`, `recoverInterruptedAIRuns`, `cleanupAIConnectionRequests`, and `butlerAutomationTick` execute successfully, and `butlerWorkspaceEvent` receives changes. Cloud Scheduler and the functions service account need their normal project permissions. Firestore TTL is configured for short-lived public request-limit records; TTL removal is asynchronous and is not relied on for authorization.
6. Configure payment credentials and webhooks through each provider's secure settings flow. Verify signatures, exact amount/currency/source matching, provider retries, payment return origins, expired holds, and a deliberately late payment in the provider sandbox. Local tests use provider fixtures; they do not certify a real sandbox integration.
7. Optional custom domains remain disabled until `CUSTOM_DOMAIN_SITE_ID` equals the dedicated storefront Hosting site and the backend service account has Hosting management permissions. Verify ownership, routing, and the certificate before enabling a domain. The runtime also checks the private verified domain record and owner/site relation on each domain route.
8. Perform collection cutover per workspace through `migrateWorkspaceCollections`, inspect its verified manifest, and confirm only the new writer is authoritative. Do not manually switch `storageMode` or write catalog/order/booking documents around these commands.

## Repeatable checks

`npm run test:backend` starts or reuses a local Firestore emulator with an explicit demo project, then runs the backend integration suites. It rejects production project IDs and non-loopback emulator addresses. Provider calls and credentials are excluded from this test runner. Cold startup on Windows was verified with all 67 integration checks passing, zero failures or skips; the six runner checks cover isolation and temporary startup failures. The runner tolerates slow startup only for the emulator it launches and closes that process after the run. The website tests use an in-memory Storage adapter; real Storage still requires the staged verification below.

`npm run release:readiness` checks **only the configuration supplied in the process environment**, the tracked Hosting rewrites, and target bindings. It never reads secret files, prints credentials, calls a provider, or deploys. Missing configuration produces a failed local readiness result. A passing result still leaves Console, approval, provider, and browser checks marked for manual verification.

Run the full Node test suite, TypeScript check, health/smoke checks, and production build after integration. Save test output outside tracked source. Do not infer successful deployment from a passing local build.

## Staged acceptance journeys

- Sign in with Google, refresh, sign out, and switch owners. Confirm no previous owner's records, pending approvals, chat history, or unsaved drafts appear.
- Enable funded included AI with a small allowance. Run Ask, Plan, and Build; stop before admission and during streaming; disconnect the browser and reload. Confirm durable recovery and clear usage-limit errors. Confirm commercial ChatGPT connection remains unavailable while gated.
- Edit/import source and assets, save, refresh, restore a cloud version, and compare a conflicting draft from another device. Verify a failed cloud save is labelled as device-only.
- Publish a valid design to the isolated site, share a read-only preview, update live catalog/settings without republishing, and restore a prior design. Verify malicious bindings, unknown IDs, unsupported operational settings, and same-origin hosting cannot publish.
- Purchase the last unit from two independent browser sessions; book the last capacity slot concurrently. Compare app and custom-site decisions. Replay checkout/payment requests, tamper with totals/currency, expire holds, and exercise late-payment exceptions.
- Prepare and dismiss/approve Butler changes inline. Change the underlying record before approval and confirm refusal. Pause/expire a routine, retry its event, and confirm frequency/daily limits and audit records.
- Check the builder, Butler, AI settings, and public journeys at desktop and 390px mobile width. Test the real hosted Storage, OAuth, domains, and payment providers before allowing a broad production rollout.

These are operational release gates. Local emulator success does not establish external partner approval, funded credentials, deployed jobs, or real provider behavior.
